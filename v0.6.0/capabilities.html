Capabilities matrix ​

These are the capabilities of the mature LBM core within Kraken's broader method-agnostic platform. For how LBM fits the platform — and what is shipped versus on the roadmap across methods — see the architecture overview.

This page is the single-source-of-truth for what the LBM core can do today, what is partially implemented, and what is out of scope. Rows were last checked against the code on dev/platform in November 2026 (after v0.5.1). Every entry links to the theory page that derives it, the example that exercises it, and the API or .krk reference that documents how to call it.

A ✓ means the feature runs and a test in test/ exercises it. Rows marked code present, later release exist in the codebase (and in some cases are fully tested) but are not part of the validated surface.

Legend: ✓ = works and tested · ~ = implemented, partial validation · — = not applicable · ✗ = not yet

  • .krk: BC types, Expressions

  • Expression whitelist: arithmetic, sin/cos/tan/exp/log/sqrt/abs/clamp, variables x, y, z, t, Lx, Ly, Lz, Nx, Ny, Nz, dx, dy, dz + Defined vars.

Limitations: thermal BCs are scalar only (no T = f(x,y,t)). In a .krk file the T = ... values on Boundary lines are used by heat_conduction cases only (one opposing pair of faces). The natural_convection and rayleigh_benard cases ignore them and use the driver values (hot = 1, cold = 0; hot west and cold east for natural convection, hot south and cold north for Rayleigh-Bénard). Outflow/Neumann/symmetry are recognized by the parser but kernels are minimal — use with caution.

4. Grid refinement (under development) ​

Grid refinement (patch and conservative AMR) is under development and not validated; it is not part of the supported feature set. No refinement capability is listed as working here. The code and its tests remain in the repository for development purposes. The reasons it is not validated are given in Limitations. The .krk Refine keyword is parsed but is under development and not validated; see directives.

Running sanity_check(setup) — and the check that run_simulation does automatically — covers the following:

Prandtl numberwarnPr < 0.1 or > 10 extreme for SRT thermal

  • .krk: Sanity checks

  • Parameter summary is printed at run-time with 2D/3D tag.

Limitations / planned:

  • No Ra-vs-N thermal BL resolution check (planned — ~ Ra^{1/4} minimum N).

  • No CFL check for prescribed-velocity advection.

  • Custom user checks not yet exposed in .krk.

9. Rheology ​

Beyond Oldroyd-B (the validated viscoelastic model), the models below are implemented in code; their validation level differs from row to row. The "GPU" column means the collision kernel is KernelAbstractions-based, which does not imply a GPU test. "Thermal coupling" is the shift of the model parameters with temperature (thermal_shift_factor); it is implemented for the generalised-Newtonian models only, and only one driver calls the thermal rheology kernel (collide_rheology_thermal_2d!, via run_natural_convection_gnf_2d, 2D natural convection, reachable from .krk).

3D generalised-Newtonian (Julia API only). run_gnf_channel_3d (D3Q19 TRT, LI-BB walls, Guo forcing; Power-law, Carreau-Yasuda, Cross) is isothermal, has no .krk keyword yet, and is verified against an exact planar-channel solution on CPU Float64 (test/analytical/gnf3d_channel_order.jl, observed order 1.93 to 2.00) and on an A100 (Float64, N = 32 to 256, order 1.95 to 2.001, archived sweep, not a test). With a constant viscosity it equals the Newtonian step (test/analytical/gnf3d_parity.jl); the strain-rate estimate is in test/analytical/gnf3d_strain_rate.jl. Bingham and Herschel-Bulkley have no 3D path. See 3D GNF channel.

3D viscoelastic (since v0.5.0). Oldroyd-B, FENE-P, Giesekus and PTT (linear and exponential) run in 3D in log-conformation form on the FVFD path only (run_viscoelastic_fvfd_poiseuille_3d, run_viscoelastic_fvfd_extensional_3d). Oldroyd-B is validated against analytic solutions and RheoTool on periodic Poiseuille and, with the velocity imposed, planar extension. The coupled planar-extension mode is not validated: two known defects of its driver (a velocity read-back after collision, issue #68, and Zou-He face rebuilds that skip the periodic z planes, issue #69) are open and recorded as broken tests. FENE-P, Giesekus and PTT against their closed-form simple-shear fixed points (FENE-P also against its transcendental planar-extension fixed point), and in the coupled flows through their Oldroyd-B limit and qualitative trends — see Viscoelastic constitutive models. The 3D LBM-CDE drivers (sphere, Couette, Poiseuille) accept Oldroyd-B only, in direct conformation form, and the sphere driver is not validated against a viscoelastic reference. The 3D viscoelastic tests run on CPU; the GPU and thermal-coupling columns above refer to 2D.

Effective viscosity dispatches at compile-time (zero-cost abstraction via Julia's JIT). See src/rheology/ (models, viscosity, strain_rate).

Not part of the validated surface ​

These features exist in the codebase (tests often pass) but are not documented as validated:

  • Multiphase (VOF + PLIC): src/kernels/vof_2d.jl, src/kernels/pressure_vof_2d.jl

  • Phase-field (Allen-Cahn): src/kernels/phasefield_2d.jl

  • Shan–Chen spinodal: src/drivers/multiphase.jl

  • Species transport: src/kernels/species_2d.jl

  • Viscoelastic cylinder driver: src/drivers/viscoelastic.jl

  • 3D generalised-Newtonian rheology: kernels are 2D only (3D viscoelastic: see §9)

  • 3D MRT: not implemented (D3Q19 BGK and TRT only)

  • Left-out test modules: conservative-tree AMR, multiblock, SLBM and Gmsh drag have test files that the default suite does not run; set KRAKEN_TEST_EXPERIMENTAL=1 to run them.
